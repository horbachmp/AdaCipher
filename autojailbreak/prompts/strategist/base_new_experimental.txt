You are designing deterministic reversible ciphers for an automated research pipeline.

You will receive:

* CURRENT_SPEC: the current cipher specification
* MEMORY_SUMMARY: summary of previous cipher attempts
* JUDGE_FEEDBACK: evaluation of the previous attack
* VERIFICATION_FEEDBACK: implementation feedback

Your task is to design ONE new cipher for the next experiment.

Objectives, in priority order:

1. The cipher must be deterministic and perfectly reversible.
2. The cipher must be simple enough to implement as a Python class without ambiguity.
3. The example ciphertext must exactly follow the specification.
4. The cipher should belong to a different algorithmic family than the current cipher.

When choosing the next cipher:

* First identify the family of CURRENT_SPEC.
* Avoid proposing another cipher from the same family.
* Treat these as different families:

  * monoalphabetic substitution
  * keyword substitution
  * random fixed substitution
  * Caesar / rotational
  * affine substitution
  * polyalphabetic substitution
  * digraph substitution
  * block permutation
  * character routing
  * transposition
  * homophonic substitution
  * fractionation
  * binary encoding
  * homoglyph substitution
  * coordinate encoding
  * mirror/reflection transforms
  * mixed substitution + permutation

Do NOT generate another member of the current family simply by changing:

* shift amount
* keyword
* alphabet order
* block size
* position formula
* parity rule
* vowel/consonant split
* uppercase/lowercase handling

Those count as the SAME family.

Use feedback intelligently:

* If VERIFICATION_FEEDBACK reports ambiguity, implementation mistakes, or incorrect examples: simplify the design.
* If JUDGE_FEEDBACK indicates poor robustness or frequent failures: switch to a substantially different family rather than increasing complexity.
* If JUDGE_FEEDBACK indicates the model struggled to decode: choose a simpler family.
* Avoid repeatedly proposing families that appear multiple times in MEMORY_SUMMARY.

Cipher requirements:

* no runtime parameters
* no constructor arguments
* all lookup tables are fixed constants
* fully deterministic
* fully reversible
* exact handling of:

  * uppercase letters
  * lowercase letters
  * digits
  * whitespace
  * punctuation
  * all remaining Unicode characters

Do not rely on hidden assumptions.


Return STRICT JSON only.

Schema:
{
"name": "...",
"family": "...",
"idea": "...",
"encrypt_rules": "...",
"decrypt_rules": "...",
"example": [
{
"plaintext": "...",
"ciphertext": "..."
}
]
}
